# DECISIONS

One line per decision not settled by PLAN.md, with the reason.

- 2026-10-12: Escalations use `fable-debugger` (availability check returned OK), `opus-debugger` only as fallback.
- 2026-10-12: Cloned menagerie with plain `git clone` + checkout of Playground's pinned SHA (identical to `ensure_menagerie_exists()`), in the background in parallel with the pip install, to save time.
- 2026-10-12: Probe scripts that are not part of the pipeline live in `scripts/dev/` (kept for transparency).
- 2026-10-12: Gravity compensation (`gravcomp="1"`) on all Panda arm/hand bodies. Menagerie's soft servos (kp 300-1000) sagged ~23 mm under gravity, which made mm-level insertion impossible; real Franka controllers compensate gravity. Peg itself is not compensated (wrist sensor still feels its 0.49 N weight). Sag now ~0.2 mm.
- 2026-10-12: Fixed gripper orientation = straight down with hand x snapped to a world axis (Playground's `home` keyframe is tilted ~7 deg, which would make a square peg unable to enter a square hole). Peg faces verified parallel to the hole walls.
- 2026-10-12: Anti-windup limit `max_servo_error` = 3 mm on all three axes (PLAN said 5 mm on z only). Measured contact stiffness is ~12 N/mm, so 5 mm let the scripted controller hit 129 N peaks; 2 mm cut peaks to 35 N but slowed free motion (servo lag ~3 mm at 1 mm/step) so success came at step ~141/200; 3 mm gives ~42 N peaks and success at step ~100.
- 2026-10-12: Hole-position observation bias applied to x,y only (z bias does not change the lateral alignment problem the experiment is about).
- 2026-10-12: Scripted controller drives the commanded setpoint (plus a slow 0.2-gain xy integral on measured error while descending), not the measured tip: integrating measured error with the servo's 3-step lag caused a limit cycle.
- 2026-10-12: Torque observation normalised by 2 N*m (force by 20 N per PLAN).
- 2026-10-12: Added `peg_insertion/jax_compat.py`: Brax 0.14.2 (latest) calls `jax.device_put_replicated`, removed in JAX 0.11 (which Blackwell needs). Shim uses JAX's documented drop-in (stack + shard over devices). Single GPU, so behaviour is identical.
- 2026-10-12: Training uses MJX `impl=warp` (installed `mujoco-warp==3.15.0`, matching mujoco 3.15). Benchmark at 1024 envs: JAX ~2.5k steps/s steady, Warp ~11k steps/s (4.4x, > the 1.3x bar in PLAN 4.6). Full test suite passes under both (`PEG_IMPL=warp pytest tests/` 12 passed, scripted 0.5 mm 100%). Eval/render use the same impl as training.
- 2026-10-12: PPO learning rate 5e-4 -> 2e-4 and budget 10M -> 20M steps (21 evals) for ALL conditions; all runs redone with this one config (old 10M results archived in results/archive/lr5e-4_10M/, not deleted). Evidence (single-knob, force@0.5mm): seed 0 at 5e-4 hit 98% at 3.4M then collapsed to 0% (eval reward 32 -> 20); seed 0 at 2e-4 held 94-100% from 2M to 20M; seed 1 at 5e-4 happened to stay stable (99%); ADAPTIVE_KL schedule never learned (0%). 20M because a lower LR learns slower and runs only take ~6 min.
- 2026-10-12: 3 seeds per condition (runs are ~6 min, PLAN allows 3 when < 30 min), plus force@2mm and force@1mm (2 seeds each) for a full force line.
- 2026-10-12: Reward `align` term changed from a 20 mm-margin Gaussian to a 5 mm-margin linear tolerance (`align_margin=0.005`), same for all conditions. Why: with lr 2e-4, pos@1mm oscillated 0-83% and ended at 0%; a rollout showed the policy descending with ~2 mm lateral error and sliding along the wall rim. The old align term was ~flat (0.998) for errors under 2 mm and `reach` is flat within 2 mm, so mm-level precision was only rewarded by actually dropping into the hole (rare at tight clearances). (PLAN Appendix B notes that Isaac Lab Factory's insertion reward also uses keypoint distances squashed at several scales; not verified independently.) Check (seed 0, 20M, run in parallel): pos 2/1/0.5 mm = 0.996/0.957/0.844, force 0.5 mm = 0.980, all stable to the end. All Phase 6 runs are redone with this final config; earlier results archived under results/archive/ (lr5e-4_10M, lr2e-4_align20mm, reward_fix_check).
- 2026-10-12: Acted on code review (code-reviewer agent): (1) chart error bars now = min-max across seeds around the mean of per-seed rates (pooled Wilson CI over seeds overstated precision; per-run Wilson CIs stay in summary.csv); (2) added a physical-validity check in the eval rollout (max per-axis lateral offset while the tip is >2 mm below the entrance must stay <= clearance + 0.5 mm, else counted as a through-wall episode) instead of changing the env mid-sweep; (3) evaluate.py refuses clearance/bias overrides without --tag; (4) run labels taken from the env's actual config; (5) nan-safe means, `still_inserted_at_end` reported. All runs are re-evaluated with the final evaluate.py after the sweep.
- 2026-10-12: Seeds 3 and 4 added for all four core conditions (pos 2/1/0.5 mm, force 0.5 mm) -> 5 seeds each, identical config (first planned for the 0.5 mm pair only; pos_1mm_s2 then also failed at 0%, so all core conditions get 5). Why: at 0.5 mm, outcomes are seed-dependent and nearly bimodal for BOTH conditions (pos s0 0% / s1 83%; force s0 100% / s1 0%), so 3 seeds cannot answer the core question. More replicates, not tuning.
- 2026-10-12: Report only deterministic 500-episode evaluations. Brax's in-training eval uses the stochastic policy; at 0.5 mm the exploration noise alone can prevent insertion (pos_0.5mm_s1: 0% stochastic in-training vs 83% deterministic final eval), so learning curves are labelled as stochastic and not used for the headline numbers.
- 2026-10-12: force@2mm and force@1mm also get a 3rd seed (s2), so every condition has >= 3 seeds.
- 2026-10-13: Rendering uses a render-only scene variant (scripts/render_scene.py) built from the same `build_xml` output with only colours/lights/cameras changed, plus a visual-only floor plate (no contact pair). Why: the user asked never to touch the training XML; replaying recorded qpos needs identical geometry, which build_render_model asserts. Cutaway (side view, near wall hidden via geom group 5) chosen over a top-down inset because it shows the peg's depth inside the hole, which a top view cannot. The inset reuses the one osmesa context with a smaller viewport (a second osmesa context renders garbage).
